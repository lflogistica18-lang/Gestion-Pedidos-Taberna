### Component Responsibilities

| Component | Responsibility | Typical Implementation |
|-----------|----------------|------------------------|
| POS View | Product selection, cart management, order creation, payment | React components with Zustand cart store |
| KDS View | Display pending orders, accept/mark ready actions | Supabase Realtime subscription on `orders` table |
| Products Admin | CRUD for products with prices and categories | react-hook-form + Supabase REST |
| Reports View | Daily sales totals, breakdown by payment method | Supabase aggregate queries with date filters |
| Order State Machine | Manage order lifecycle (Pendiente → Listo) | DB status column + `order_status_log` table |
| Realtime Layer | Push order changes to KDS without polling | Supabase `postgres_changes` channel |
| Service Worker | PWA caching, installability | vite-plugin-pwa with Workbox |
| Row Level Security | Protect data at DB level | Supabase RLS policies |

### Structure Rationale

- **modules/**: Feature-first organization. Each module is self-contained with its own components, hooks, and page. Easy to work on POS without touching KDS.
- **shared/**: Cross-cutting concerns. Supabase client, common UI components, shared hooks.
- **supabase/**: Database migrations separate from app code. Version-controlled schema changes.
- **types/**: Auto-generated from Supabase schema. Single source of truth for DB types.

## Architectural Patterns

### Pattern 1: Supabase Realtime Subscription (KDS)

**What:** Kitchen display subscribes to order changes via WebSocket, no polling.
**When to use:** Any view that needs live updates (KDS is the primary case).
**Trade-offs:** Low latency, low bandwidth. Requires handling reconnection.

**Example:**
```typescript
// hooks/useKdsOrders.ts
const channel = supabase
  .channel('kds-orders')
  .on(
    'postgres_changes',
    {
      event: '*',
      schema: 'public',
      table: 'orders',
      filter: 'status=in.(pendiente,en_preparacion)'
    },
    (payload) => {
      // Update local state with new/changed order
      handleOrderChange(payload)
    }
  )
  .subscribe()
```

### Pattern 2: Optimistic Updates (POS Cart → Order)

**What:** Show order as "created" immediately, sync to DB in background.
**When to use:** Order submission from POS — cashier shouldn't wait for network round-trip.
**Trade-offs:** Faster UX, but needs error handling if DB write fails.

**Example:**
```typescript
// Create order optimistically
const submitOrder = async (cart, paymentMethod) => {
  const optimisticOrder = { ...cart, status: 'pendiente', id: tempId() }
  addToLocalOrders(optimisticOrder) // Show immediately

  const { data, error } = await supabase
    .from('orders')
    .insert({ items: cart.items, payment_method: paymentMethod, total: cart.total })
    .select()
    .single()

  if (error) rollbackOptimistic(optimisticOrder.id)
  else replaceOptimistic(optimisticOrder.id, data)
}
```

### Pattern 3: Device-Based Role (No Auth in v1)

**What:** Instead of login, each device navigates directly to its view (POS or KDS).
**When to use:** Small trusted team (3-5 people), no sensitive data requiring per-user access control.
**Trade-offs:** Simple, zero friction. Not secure for untrusted environments.

**Implementation:** Cashier bookmarks `/pos`, kitchen bookmarks `/kds`. NavBar lets you switch.

### Pattern 4: Product Price Snapshot in Order Items

**What:** Store the price at time of order, not a reference to current product price.
**When to use:** Always — prices change weekly, historical orders must retain original price.
**Trade-offs:** Slight data duplication, but critical for accurate reporting.

**Example:**
```sql
CREATE TABLE order_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id UUID REFERENCES orders(id),
  product_id UUID REFERENCES products(id),
  product_name TEXT NOT NULL,       -- snapshot
  unit_price NUMERIC NOT NULL,      -- snapshot at time of order
  quantity INTEGER NOT NULL,
  notes TEXT,
  subtotal NUMERIC GENERATED ALWAYS AS (unit_price * quantity) STORED
);
```

## Data Flow

### Order Lifecycle

```
[Cajero: POS View]
    │
    │ 1. Select products, add notes, choose local/delivery
    │ 2. Select payment method
    │ 3. Submit order
    ▼
[Supabase: INSERT orders + order_items]
    │
    │  status = 'pendiente'
    │  → INSERT order_status_log (action: 'created')
    │  → Realtime broadcasts to KDS
    ▼
[Cocinero: KDS View]
    │
    │ 4. Sees new order appear
    │ 5. Taps "Aceptar"
    ▼
[Supabase: UPDATE orders SET status = 'en_preparacion']
    │
    │  → INSERT order_status_log (action: 'accepted')
    │  → Realtime broadcasts update
    ▼
[Cocinero: KDS View]
    │
    │ 6. Finishes cooking, taps "Listo"
    ▼
[Supabase: UPDATE orders SET status = 'listo']
    │
    │  → INSERT order_status_log (action: 'ready')
    │  → Realtime broadcasts update
    ▼
[Cajero/Mozo: marks delivered]
    │
    │ 7. Taps "Entregado"
    ▼
[Supabase: UPDATE orders SET status = 'entregado']
    │  → INSERT order_status_log (action: 'delivered')
```

### Database Schema

```sql
-- Products
CREATE TABLE products (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name TEXT NOT NULL,
  category TEXT NOT NULL CHECK (category IN ('comida', 'bebida', 'postre')),
  price NUMERIC NOT NULL CHECK (price >= 0),
  active BOOLEAN DEFAULT true,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now()
);

-- Orders
CREATE TABLE orders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_number SERIAL,
  type TEXT NOT NULL CHECK (type IN ('local', 'delivery')),
  status TEXT NOT NULL DEFAULT 'pendiente'
    CHECK (status IN ('pendiente', 'en_preparacion', 'listo', 'entregado')),
  payment_method TEXT NOT NULL CHECK (payment_method IN ('efectivo', 'debito', 'transferencia')),
  total NUMERIC NOT NULL CHECK (total >= 0),
  notes TEXT,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now()
);

-- Order Items (with price snapshot)
CREATE TABLE order_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id UUID REFERENCES orders(id) ON DELETE CASCADE,
  product_id UUID REFERENCES products(id),
  product_name TEXT NOT NULL,
  unit_price NUMERIC NOT NULL,
  quantity INTEGER NOT NULL CHECK (quantity > 0),
  notes TEXT,
  subtotal NUMERIC GENERATED ALWAYS AS (unit_price * quantity) STORED
);

-- Order Status Log (audit trail)
CREATE TABLE order_status_log (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id UUID REFERENCES orders(id) ON DELETE CASCADE,
  action TEXT NOT NULL,
  previous_status TEXT,
  new_status TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

### State Management

```
[Zustand Store: Cart]
    ↓ (POS adds items)
[Cart State] → [Submit] → [Supabase INSERT] → [Realtime] → [KDS State]
                                                    ↓
                                              [Zustand Store: KDS Orders]
```

## Scaling Considerations

| Scale | Architecture Adjustments |
|-------|--------------------------|
| 3-5 users (current) | Single Supabase project, free tier, no caching needed |
| 10-20 users | Still fine on free tier. Add connection pooling if slow |
| 50+ users | Upgrade Supabase plan. Consider Edge Functions for complex reports |
| Multi-branch | Separate schemas or projects per branch. Major architectural change |

### Scaling Priorities

1. **First bottleneck:** Realtime connection limits (200 on free tier) — won't hit with 3-5 devices
2. **Second bottleneck:** Report query speed as order volume grows — add DB indexes on `created_at` and `status`

## Anti-Patterns

### Anti-Pattern 1: Polling Instead of Realtime

**What people do:** `setInterval` to fetch orders every 5 seconds
**Why it's wrong:** Wastes bandwidth, 5-second delay, battery drain on tablets
**Do this instead:** Supabase Realtime subscription — instant, efficient

### Anti-Pattern 2: Referencing Current Price in Order Items

**What people do:** `order_items.product_id` → JOIN to get price at report time
**Why it's wrong:** Price changes break historical order totals
**Do this instead:** Snapshot `unit_price` and `product_name` into `order_items` at creation time

### Anti-Pattern 3: No Status Audit Log

**What people do:** Just update `orders.status` without logging
**Why it's wrong:** Lose timing data (how long in kitchen?), can't debug disputes
**Do this instead:** `order_status_log` table with timestamps for every transition

### Anti-Pattern 4: Full Page Navigation Destroying Subscriptions

**What people do:** Navigate away from KDS, losing the realtime channel
**Why it's wrong:** Reconnection takes time, orders appear delayed
**Do this instead:** Keep subscription alive at app level, or use SPA routing (no full page reload)

### Anti-Pattern 5: Showing UUID as Order Number

**What people do:** Display `a1b2c3d4-e5f6...` to kitchen staff
**Why it's wrong:** Impossible to reference verbally ("order alpha-one-bravo...")
**Do this instead:** Use `SERIAL` `order_number` — short, human-readable, daily or sequential
